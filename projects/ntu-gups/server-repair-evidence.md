# GUPS 工作站報修與連線身分核對

## 已確認進度

- 第二台工作站已完成供應商報修通知。使用者確認顯示線接在獨立顯示卡 HDMI，仍無畫面；網路線換過網孔後仍無反應。機內燈號亮只證明有供電，故障原因與是否完成開機仍待檢查。
- 報修信使用已核准正文回覆原信串、保留核准副本並附上兩張原始 JPEG。已核對實際寄件備份 MIME 的寄件帳號、收件人、副本、正文、In-Reply-To 與兩張附件原始位元組。這不證明供應商已收件、閱讀或安排維修；未建立自動監看。
- 當次 dock 有線連線與 SSH 後來成功，但讀回主機名稱、網卡及位址後，確認連到的是原本已知主機的另一個網孔，不能當作故障第二台已恢復。聯絡資訊、實際設備位址、郵件識別碼及照片保留於私人記錄。

## 後續排查方法

- 先用 USB 裝置樹對照網卡的 BSD 介面名稱，再看 carrier、鄰居與 SSH。該次外接 dock 使用 Realtek RTL8153，不能只憑網路服務名稱判定它對應哪個實體孔。
- 該次 macOS 的 `system_profiler SPUSBHostDataType` 能列出 USB Hub 與網卡；舊 `SPUSBDataType` 沒輸出，不能據此判定裝置未被辨識。
- 有 carrier 但沒有 DHCP 位址時，可先在指定有線介面做 IPv6 link-local 鄰居探索，再測 SSH；此次不必啟用共享或修改伺服器網路設定就完成連線核對。必須保留介面 scope，並嚴格驗證既有主機金鑰；開放的 SSH 埠本身不證明設備身分。
- 開機與硬體故障報告只寫已觀察症狀和使用者確認的接線。顯示、網路均無回應仍不足以確診主機板、網卡或作業系統故障。

## 原生 Mail 驗證與同步界線

- 附件載入及已保存草稿的 MIME source 更新可能不同步。第一次保存曾只讀到一張照片；等待載入完成後，重讀來源才核實兩張。送出前須確認完整附件與核准正文，不能只信畫面或 `send` 回傳值。
- Rich text 讀回可能多出 U+2028；純文字 MIME 可能加入引用前綴及附件占位字元。可辨認格式差異，但仍須以實際 HTML 正文及所有附件的位元組核對，不能放過缺字、額外正文或漏附件。
- 本機 Codex ad-hoc 記憶庫沒有 remote，不是省略同步的理由。把可公開的長期知識整理到既有 canonical 共享記憶庫，通過檢查後 commit、push 並核對遠端；最後刷新 QMD、向量與查詢回讀。本機索引成功不等於遠端同步完成。
