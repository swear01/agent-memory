---
title: 以端到端牆鐘時間判斷快慢
scope: global workflow performance
status: active
updated: 2026-11-27
---

使用者說「越快越好」時，目標是從開始工作到拿到可驗證成果的實際總耗時。這項偏好適用於所有任務。

- 用獨立於被測程式的單調時鐘，記錄從同一起點到可驗證完成條件的牆鐘時間。把啟動、準備、工具來回、等待、重開、重試和驗證都計入，並記錄成功產出。比較方案時使用相同成果門檻，說清楚起點和量測條件。
- 也量自動化腳本的指令從送出到應用程式確認有多快，並記錄原生動作和寫入結果的時間。若固定等待或輪詢拖慢反應，縮短後保留原生驗證，再用實際流程核對整體用時。
- 優先找出最耗時的環節。把可預先規劃或依狀態推進的步驟寫進一個有明確停止條件的批次，讓批次自己讀狀態、按原規則執行、處理可恢復失敗並驗證結果。可以累積且不影響中途成功率的結算、兌換或升級，集中在批次邊界執行，省去重複進出介面和來回操作。
- 保留可繼續使用的程序、會話和中間產物。把常調整的策略留在可即時更新的腳本或設定。只有部署依賴、程序狀態或驗證本身需要時才重開，並把冷啟動與暖態迭代分別記錄。
- 產品內部時間、FPS、設定倍率或單一 API 延遲可用來定位瓶頸。判斷方案快慢時，回到同一成果所需的真實秒數；若成果可以重複，補看每分鐘的有效產出與失敗代價。
- 使用者正在用電腦時，從 CLI 或應用程式內 API 完成操作、狀態查詢、結算與驗證。視窗焦點、滑鼠和桌面鍵盤由使用者掌控。不為了看畫面或確認結果而切換前景。確認應用程式處於失焦背景時仍能執行並以原生狀態驗證實際進度。常駐批次應能從 CLI 查進度、調整接下來的步驟或安全停止。
- 長批次逐回合記起訖、階段耗時和已保存的淨產出，才能分辨反應延遲、固定往返和無效重試。先驗證連續無產出的換工作條件，避免一趟空手就切掉有效批次。安全且有成熟批次可跑時，讓它繼續執行，從旁分析新策略。
遊戲加速的設定值、注入狀態與肉眼速度要和外部秒錶分開查。從相同場景量實際遊戲幀、由出發到原生存檔的總用時與已入帳產出。倍率仍顯示啟用、實測卻接近原速時，回復並驗證實際吞吐量，再使用所要求的倍率。
